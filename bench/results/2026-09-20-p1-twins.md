# P1 twins against their baselines — 2026-09-20

The first slice measured: `tick`, `chain` and `wide_chain` on this runtime,
beside the same three scenarios on hgraph's C++ runtime, measured back to
back on a quiet machine. The baselines of
[2026-09-19](2026-09-19-cpp-baselines.md) were re-measured in the same
session, because that file asked for it.

## Conditions

| | |
|---|---|
| Machine | The owner's private Linux validation host: AMD Ryzen Threadripper 9980X (64 cores), Ubuntu 26.04.1 LTS, governor `performance` |
| hgraph | `36c054c` (main, "Merge pull request #1016"), core only, as before. The baseline binary is the one built on 2026-09-19; its sources are unchanged |
| C++ | g++ 14.3.0, `-O3 -DNDEBUG` (CMake `Release`), C++23 |
| Rust | rustc 1.98.1, `--release`: thin LTO, one codegen unit |
| Method | `cargo xtask bench --samples 15 --pin 8`: 15 fresh-process samples, pinned to core 8 |
| Load average | 0.25 before, 0.63 after (1 minute); the 5- and 15-minute figures stayed under 0.25 throughout |
| Timed | The run only: building the graph and the executor is outside the clock on both sides |

Every sample passed its own checksum check, and for each scenario the two
halves agree on the checksum, on the number of nodes, and on the number of
times the sink was evaluated.

## Reading them

- The baselines reproduce: on an idle machine they came out 0.4% to 0.9%
  above the figures of 2026-09-19, inside the spread of either session. The
  2026-09-19 numbers can be trusted as targets.
- A node costs this runtime about **11 ns** to evaluate where the reference
  spends about **65 ns**. `chain` and `wide_chain` agree on both sides, so
  the figure is the per-node cost and not a fixed cost spread thin.
- `tick` gains most (11×) because it is nearly all fixed cost: three nodes,
  and a source through the node scheduler every cycle. The reference pays
  274 ns of cycle overhead there; this runtime pays 26 ns.
- `wide_chain` gains no more than `chain`, which is what the ready set was
  built for: a tree of bitmaps costs about the same per evaluated node at
  102 nodes and at 961.
- The gap is wider than a 5% budget needs, and it should be read narrowly.
  The prototype is P1: `i64` and `bool` scalars, static node types, no
  dictionary, no reference, no nested graph, no real time. The reference
  carries the whole of its type machinery through the same path. What the
  figures establish is that the data layout of
  [0009](../../docs/explorations/0009-designing-for-speed.md) has headroom,
  not that the finished runtime will keep it.
