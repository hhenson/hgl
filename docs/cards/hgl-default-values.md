# Card: hgl-default-values

The default_values policy checks general required ordinary expressions through the authoritative frontend checker. It may use ir, library, value_eval, value_types, inheritance and enums; initial budget 220 lines within the unchanged semantics cap.

Public surface: error, required, parameters, declaration, bindings, pending, contextual, literal and size_environment. Concrete type formation precedes required evaluation. Exact contextual list fixedness remains required. Temporal literals retain their cold contextual recipes. Known missing Any capabilities map to source category type/value.constant_capability, distinct from runtime value.capability.

Every unused declaration checks its closed defaults, including known field types in generic structures and closed parameter defaults in generic or required-const functions. Dependent type/default expressions remain deferred until concrete checking. Inherited fields retain their declaring type scope. Constructor finish_checked fills missing defaults in resolved field order through that same checker. Signature::parameter_names centralizes argument order; Parameter::value_default retains checked ordinary constant IR separately from source syntax.

Acceptance: the mixed source fixture with four coded rejections plus runtime/positive controls; recursive list[0].field and tuple[0][0] selectors; generic and required-const closed defaults; exact fixedness rejection. Existing scalar/contextual defaults and const size checking retain their contracts.

Direct graph and suite compiler entry points validate closed required defaults before constructing plans, including unused declarations. Reachability rules for ordinary function bodies remain unchanged.

Defaults resolve in their defining enclosing module/lexical closure before formal and instance-field bindings. Complete generic substitution retains that closure. Lifted ordinary defaults and explicitly fixed ordinary eval arguments become retained node configuration; temporal parameter defaults remain excluded.

Parameter checking has two explicit phases. Closed defaults are materialized
before dependent size annotations; supplied constant arguments take precedence
when forming that size environment. The retained values are borrowed for size
resolution instead of cloned and re-evaluated. After ordinary argument inference,
parameters receives the inferred type environment and checks every remaining
resolvable default in its declaration closure. Previously retained defaults are
reused. Formal parameter values never enter the default expression environment.
Eval adapters repeat only deferred default checking after temporal arguments
provide the remaining generic types.

Controls execute imported generic computed defaults with a conflicting caller
declaration, dependent fixed-size defaults, zero-size defaults and explicit
arguments, and preserve required capability, exact-type and null diagnostics.
The two regression controls fail on the prior head with missing fallback and
unknown size-name errors respectively.

Default dependencies follow type positions in explicit applications and lambda
annotations. A callable or value spelling that matches a type parameter does
not defer an otherwise closed default. Declaring-owner parameter patterns are
resolved against the concrete root bindings; unresolved patterns remain deferred.
The frontend installs these exact bindings while checking the expression, then
restores its caller environment. Parameter-default errors retain their declaring
source as well as their original expression span across overload selection.

pending preserves the no-default/already-retained fast path. contextual owns
the existing direct contextual-field test for run preparation; it adds no new
provider eligibility. Constructor checking and declaration checking share the
same resolved default-owner bindings, including concrete inherited specializations.

Eval argument preparation retains omitted ordinary value-function defaults alongside
explicit const defaults. Written arguments retain source order; omitted defaults
follow in declaration order. Each recipe is materialized once before the lifted
node executes, even when its parameter is unused; a supplied value suppresses it.
